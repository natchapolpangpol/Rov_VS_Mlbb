# บทสาธิต 8–10 นาที

สถานะ: มี pipeline, ข้อมูลจริงสามแหล่ง, ผลวิเคราะห์และหลักฐานตรวจระบบแล้ว ผลข้อมูลจริงติด partial ตามข้อจำกัดเดิม

## 1. อธิบายปัญหาและผลส่งมอบ — 1 นาที

“งานนี้เตรียมข้อมูลให้ผู้วิเคราะห์คอนเทนต์เกมเปรียบเทียบการค้นหา วิดีโอ และรีวิวในระดับเกมต่อเดือน ส่วนที่พัฒนาต่อคือกระบวนการตรวจคุณภาพ เก็บประวัติ รันซ้ำ ตั้งเวลา และตรวจที่มาของผลลัพธ์ได้”

เปิด [แผนผัง](architecture.md) อธิบาย raw → clean → summary → SQLite/exports → notebook
ระบุว่างานกลุ่มเดิมมีส่วนเก็บข้อมูล/วิเคราะห์ และส่วนที่พัฒนาต่อต้องให้เครดิตตามผู้ลงมือจริง ไม่อ้างเป็นงานส่วนบุคคลทั้งหมด

## 2. รันระบบจำลอง — 2 นาที

```powershell
.\.venv\Scripts\python.exe scripts/demo.py
```

บอกก่อนว่าข้อมูลนี้เป็น synthetic fixture เพื่อสาธิตระบบ ไม่ใช่ผลความนิยมของเกม
สคริปต์สร้างโฟลเดอร์ใหม่ใต้ `artifacts/demos/` ทุกครั้ง แล้วแสดง:

1. รันสองรอบ observations ยังเป็น 28 รายการ แต่มีประวัติแยกรอบ
2. ใส่คะแนน 99 แบบจงใจให้ผิด ระบบบันทึก failed และไม่ทับผล complete ล่าสุด
3. คืนข้อมูลเดิมและรันใหม่ได้โดยไม่เพิ่ม logical duplicates
4. จำลอง transient failure สองครั้งแล้วสำเร็จครั้งที่สาม แสดง backoff ที่ควรเป็น 2, 4 วินาที โดยไม่ใช้ network หรือหน่วงเวลาจริงในการสาธิตนี้

เปิด `evidence.json` ที่คำสั่งพิมพ์ และรายงาน recovery ที่อ้างในไฟล์นั้น

## 3. ตรวจที่มาข้อมูล — 1 นาที

เปิด manifest ของ recovery run ให้ดู raw SHA-256, input/accepted/duplicate/rejected counts และ coverage
เปิด raw กับ clean ของ Play Store เพื่ออธิบายว่ารีวิวซ้ำหนึ่งแถวถูกนับแยก ไม่หายไปโดยไม่มีเหตุผล
ชี้ให้เห็นว่า SQLite แยก content version ออกจาก run membership จึงทั้ง deduplicate และตรวจผลเก่าได้

## 4. แสดง notebook — 2 นาที

เปิด `notebooks/analysis.ipynb` ด้วย `.venv` kernel แล้ว Run All
ค่าเริ่มต้นเป็น latest complete sample จาก `config/sample.json` ซึ่งต้องรันก่อนตาม README
เลือกเกมและเดือน กด Apply filters แสดงว่ากราฟกับตารางอ้าง run เดียวกัน
อธิบายว่าข้อมูลขาดยังเป็น null ส่วนศูนย์จะใช้เมื่อ coverage ครบและไม่พบรายการเท่านั้น
ชี้ยอดวิวว่าเป็นยอดสะสม ณ วันเก็บ แบ่งตามเดือนเผยแพร่ ไม่ใช่ยอดวิวที่เพิ่มภายในเดือน

## 5. แสดงหลักฐาน timer จริง — 1 นาที

เปิด [verification](verification.md) และ evidence JSON ของ scheduler
ให้ดู `auto_scheduled=true`, เวลาที่ควรเริ่ม, เวลาที่เริ่มจริง, Completed สองรอบ และจำนวน observations ที่ไม่เพิ่ม
หลักฐานนี้เป็นการตั้งเวลา sample จริง ไม่ใช่ live collection จากสาม API
หากต้องการสาธิตสด ใช้ `scripts/verify_schedule.py` และเผื่อเวลา 2–5 นาทีเพิ่มจากบทนี้

## 6. แสดงข้อมูลจริงและขอบเขตของข้อสรุป — 1–2 นาที

เปิด [historical findings](historical_findings.md) และ report ของ run `fd1a7d895cb3477ea72591e4199e5e38`
แสดงกราฟจริง: MLBB มีคลิป 259 → 542 ในช่วงเปรียบเทียบ แต่เมื่อจำกัดช่องร่วมเป็น 259 → 366 อธิบายว่าการเปลี่ยนกลุ่มช่องมีผล
แสดงเดือนต้น/ท้ายที่ทำเครื่องหมายกากบาท และการแยก unknown collection time ออกจาก export time
รีวิวมีถึง 4 กุมภาพันธ์ 2026 จึงไม่สรุปว่าจำนวนรีวิวทั้งเดือนลดลง ส่วนยอดวิวเป็นยอดสะสมที่ไม่ทราบวันเก็บเดิม
ชี้ตาราง UTC/เวลาไทยเพื่อแสดงการตรวจสมมติฐาน ไม่อ้างว่าพิสูจน์เขตเวลาที่ถูกต้องแล้ว

เปิด notebook ข้อมูลจริงโดยตั้ง ROV_RUN_DIR ตาม README หรือเปิด artifacts/real/historical_analysis.executed.ipynb ที่รันไว้แล้ว
การสาธิต snapshot นี้ไม่ต้องต่อ Firestore หรือใช้ YouTube API key

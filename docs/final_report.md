# RoV vs MLBB: ระบบเตรียมข้อมูลหลายแหล่งสำหรับวิเคราะห์คอนเทนต์เกม

ฉบับส่งมอบ 2 พฤศจิกายน 2026 | Python 3.13 / SQLite / Prefect | ทำงานบน Windows

## บทคัดย่อ

โครงงานนี้ต่อยอด notebook ของทีมให้เป็นระบบรับข้อมูล ตรวจคุณภาพ เก็บประวัติ และสร้างชุดข้อมูลระดับเกม–เดือนที่รันซ้ำได้
ใช้ YouTube และ Google Play Store จาก Firestore ของงานเดิม ร่วมกับ Google Trends ที่เก็บย้อนหลังใหม่ในสเกลเดียวกัน
ช่วงศึกษาคือ 1 มกราคม 2025–10 มีนาคม 2026 ตาม notebook เดิม มีข้อมูลผ่านกฎคุณภาพ 22,238 แถว และผลสรุป 30 เกม–เดือน
ผลยังเป็น partial เพราะความไม่ครบถ้วนและข้อจำกัดการเลือกข้อมูลถูกเก็บไว้ ไม่เปลี่ยนให้เป็น complete เพียงเพราะโค้ดทำงานสำเร็จ

ส่วนที่เพิ่มจากการดึงข้อมูลแล้ววิเคราะห์คือ data contract, raw/clean/summary, provenance, quality gate, การป้องกันข้อมูลซ้ำ, transactional storage, orchestration และหลักฐานทดสอบการทำงานเมื่อข้อมูลผิด
ผู้ใช้สมมติของชุดข้อมูลคือผู้วิเคราะห์หรือครีเอเตอร์คอนเทนต์เกม ยังไม่มีการสัมภาษณ์ผู้ใช้หรือวัดผลการใช้งานจริง

## คำถามและขอบเขต

ศึกษาการเปลี่ยนแปลงของดัชนีการค้นหา จำนวนคลิปในช่องที่เลือก และคะแนนรีวิวที่เข้าถึงได้
ไม่สร้างคะแนนความนิยมรวมโดยให้น้ำหนักที่ไม่มีเหตุผลรองรับ และไม่ใช้ข้อมูลนี้พิสูจน์จำนวนผู้เล่นหรือการย้ายเกม

จาก notebook เดิมตรวจพบว่าเวลาของแต่ละแหล่งมีความหมายต่างกัน: YouTube มีวันเผยแพร่คลิปแต่ไม่บันทึกเวลาเก็บยอดวิว รีวิวมีเวลาแบบไม่มีเขตเวลา และ Trends เดิมต่อคำขอที่ normalize แยกช่วงกัน
จึงต้องแก้ความหมายและที่มาของข้อมูลก่อนสรุปผล ดู [การเชื่อม notebook กับ Firestore](firestore_notebook_mapping.md)

Trends เป็นดัชนีจากตัวอย่างการค้นหา ปรับตามเวลาและพื้นที่แล้วแสดง 0–100 จึงไม่ใช่จำนวนค้นหาจริง การใช้คำขอร่วมเป็นวิธีออกแบบของโครงงานให้สองคำมีสเกลเดียวกัน [Google Trends data FAQ](https://support.google.com/trends/answer/4365533?hl=en)

## สถาปัตยกรรมและ data model

รายละเอียดและแผนผังอยู่ใน [architecture](architecture.md) ลำดับหลักคือรับข้อมูล → เก็บ raw พร้อม hash → validate/clean → สรุปแต่ละแหล่งเป็นเกม–เดือน → เชื่อม → commit SQLite → CSV/Parquet/report

| ชั้น | หน้าที่ |
|---|---|
| Raw | สำเนา input ต่อ run ไม่เขียนทับ พร้อม config และ SHA-256 |
| Clean/rejected | schema กลางและเหตุผลตัดแถว มี row index ย้อนกลับ raw |
| Observations | เนื้อหาแต่ละ version แยกจากประวัติการเรียกใช้งาน |
| Run membership | ระบุว่ารอบใดใช้ข้อมูล version ใด หนึ่ง logical record ต่อรอบ |
| Summary | หนึ่งแถวต่อ run × เดือน × เกม จึงไม่เกิดการคูณแถวจาก join ข้อมูลคนละ grain |

เลือก SQLite เพราะรันในเครื่องได้ ไม่ต้องพึ่งบัญชี Firestore ทุกครั้ง และเหมาะกับขนาดข้อมูลนี้ ใช้ UNIQUE keys ร่วมกับ transaction และ writer lock
ฐานข้อมูลเก็บประวัติการรันเพิ่มได้โดยไม่สร้าง observation เดิมซ้ำ แนวทางใช้ constraint อ้างอิง [SQLite CREATE TABLE](https://www.sqlite.org/lang_createtable.html)

เก็บเวลาที่ไม่ทราบเป็น null ผ่าน packet schema v2 และแยกวัน export ออกจาก original collection time
Firestore updateTime ใช้เป็นเพียง upper bound ไม่อ้างว่าเป็นวันเก็บยอดวิว ดู [data dictionary](data_dictionary.md)

## คุณภาพข้อมูลและการรับมือข้อผิดพลาด

ตรวจ game/key, rating 1–5, views/likes ไม่ติดลบ, finite numeric values, timestamp, coverage และ Trends interval overlap
Exact duplicates เหลือหนึ่งรายการพร้อมนับจำนวน ส่วน conflicting duplicates ตัดทั้งกลุ่มออกเพื่อไม่เลือกค่าตามอำเภอใจ
สมการตรวจบัญชีคือ input = accepted + duplicates + rejected

หาก rejected fraction เกิน threshold ให้ run เป็น failed และไม่ commit accepted data/summary ของรอบนั้น
ผล partial แสดงได้แต่ไม่ทับ latest_complete เมื่อเก็บข้อมูลไม่ครบ ค่า missing ยังเป็น null ไม่ใช่ศูนย์
ข้อผิดพลาดการเขียน pointer หลัง commit แยกจากความล้มเหลวก่อน commit เพื่อไม่อ้างว่าข้อมูลในฐาน rollback ทั้งที่ commit แล้ว

## การจัดลำดับงานและผลตรวจระบบ

Prefect จัดลำดับ prepare → report และมีเส้นทาง refresh ที่ collect ก่อน prepare โดยตรวจสถานะก่อนทำงานต่อ
ตั้งเวลาแบบ local process ตาม [Prefect local deployments](https://www.prefect.io/docs/v3/how-to-guides/deployment_infra/run-flows-in-local-processes)
เครื่องและ process ต้องทำงานอยู่ การปิดจอไม่ใช่การปิดเครื่อง และ Sleep/การปิดเครื่องจะหยุดงานในเครื่อง

- ทดสอบ 45 กรณีผ่านใน environment แยกที่ติดตั้งจาก lock file
- รันข้อมูลจริงซ้ำ จำนวน observations ในฐานยัง 22,580 เท่าเดิม (รวม pilot แยก 342 รายการ) โดยประวัติ run เพิ่ม
- Timer จริงเริ่ม sample สองรอบอัตโนมัติและจบ Completed; มี 28 observations เท่าเดิม
- Demo แสดง rating 99 → failed → แก้แล้ว recovery โดยไม่ทับผล complete ล่าสุด
- Retry จำลอง transient failure สองครั้งก่อนสำเร็จครั้งที่สาม แยกจากหลักฐานเรียก API จริง
- Notebook ข้อมูลจริงรันครบ 5 code cells และตรวจกราฟที่ส่งออกแล้ว

หลักฐาน run IDs, timestamps และคำสั่งตรวจซ้ำอยู่ใน [verification](verification.md)

## ผลวิเคราะห์

เปรียบเทียบเมษายน–กรกฎาคมกับสิงหาคม–พฤศจิกายน 2025 ช่วงละ 122 วัน ภายในช่วงรีวิวที่มีข้อมูล เป็นการเลือกหลังตรวจ coverage เพื่อบรรยายชุดข้อมูล ไม่ใช่ causal design

| เกม | ดัชนีค้นหา ก่อน → หลัง | คลิป ก่อน → หลัง | คะแนนรีวิว ก่อน → หลัง |
|---|---|---|---|
| RoV | 33.52 → 32.09 | 1,090 → 885 | 2.84 → 2.39 |
| MLBB | 2.60 → 5.22 | 259 → 542 | 3.28 → 3.81 |

MLBB มีสัญญาณเพิ่มขึ้นในชุดข้อมูลนี้ แต่ RoV ยังมีดัชนีค้นหาและคลิปสูงกว่าในทั้งสองช่วง
จำนวนช่องที่มี MLBB เพิ่มจาก 12 เป็น 18 หากจำกัดเฉพาะช่องร่วม จำนวนคลิปเปลี่ยนจาก 259 เป็น 366 จึงไม่ควรอ่านการเพิ่มทั้งหมดว่าเกิดจากพฤติกรรมของกลุ่มเดิม
คะแนนรีวิวได้รับผลจากวิธีคัดเลือกที่ต่างกัน และไม่แสดงถึงผู้เล่นทั้งหมด

การตีความรีวิวเป็น UTC เทียบ Asia/Bangkok ทำให้ 90 รีวิวเปลี่ยนเดือน คะแนนเฉลี่ยช่วงเมษายน 2025–มกราคม 2026 ต่างสูงสุดประมาณ 0.0283
แต่ MLBB กุมภาพันธ์ 2026 ต่างประมาณ 0.239 เพราะมีข้อมูลถึงวันที่ 4 เท่านั้น กราฟจึงแยกจุดเดือนต้น/ท้ายที่ขาดช่วงและไม่ลากเส้นต่อให้เหมือนแนวโน้มตกลง
ผลเต็ม สูตร ตาราง sensitivity และข้อจำกัดอยู่ใน [historical findings](historical_findings.md)

## สิ่งที่ตอบอาจารย์ได้และงานต่อยอด

“งานนี้ทำระบบเตรียมข้อมูลที่ตรวจสอบและรันซ้ำได้ครับ ผลส่งมอบเป็นชุดข้อมูลเกม–เดือนพร้อมที่มาและระดับความครบถ้วน มีการเก็บข้อมูลดิบ ตรวจแถวผิด ป้องกันข้อมูลซ้ำ ตั้งเวลารัน และทดสอบกรณีล้มเหลว ส่วนรายงานเป็นตัวอย่างการใช้ข้อมูลที่ระบบผลิตครับ”

ความเชื่อมโยงกับบทเรียนอยู่ใน [course alignment](course_alignment_review.md) เป็นการเทียบเนื้อหาที่สอน ไม่ใช่คำยืนยัน rubric จากอาจารย์
หากต่อยอด ควรบันทึก collected_at ทุกแหล่ง ใช้วิธีเลือกรายการรีวิวที่สอดคล้องกัน ตรึง channel panel และเก็บ query provenance ตั้งแต่ต้น
การติดตามยอดวิวเป็นระยะจึงจะเปิดทางให้วิเคราะห์ส่วนเพิ่มตามช่วงเวลาอย่างมีหลักฐาน

ต้นทางและ notebook เดิมเป็นงานกลุ่ม ส่วนระบบใน repository นี้เป็นการต่อยอดที่จัดทำด้วยความช่วยเหลือของ coding assistant ควรระบุหน้าที่ของแต่ละคนตามที่ทำจริงเมื่อนำเสนอ

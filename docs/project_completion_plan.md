# แผนพัฒนา RoV vs MLBB จนพร้อมส่งงาน

สถานะ: implementation และข้อมูลจริงสามแหล่งเสร็จแล้ว ตรวจระบบ 45 กรณีและ demo จากโฟลเดอร์ส่งมอบผ่าน ปลายทาง GitHub คือ natchapolpangpol/Rov_VS_Mlbb ดู work_status.md และ verification.md เป็นสถานะปัจจุบัน รายละเอียดระยะด้านล่างเป็นแผนต้นฉบับ

การปรับขอบเขตล่าสุด: ผู้ใช้ได้รับสิทธิ์ Firestore ของทีมและ export ครบแล้ว ใช้เป็น raw archive แต่คง SQLite เป็นฐานหลักสำหรับรันซ้ำในเครื่อง ไม่ต้องพึ่ง Firestore ทุกครั้ง

วันที่จัดทำ: 2 พฤศจิกายน 2026

## 1. เป้าหมายเมื่อทำเสร็จ

พัฒนา Data Pipeline สำหรับรวบรวม ตรวจคุณภาพ และเชื่อมข้อมูลความสนใจต่อ RoV และ MLBB จาก Google Trends, YouTube และ Google Play Store เพื่อส่งมอบชุดข้อมูลและรายงานให้ผู้วิเคราะห์คอนเทนต์เกม

งานต้องแสดงให้เห็นทั้งคุณค่าของข้อมูลและคุณภาพของกระบวนการ ได้แก่ รันครบจากต้นจนจบ รันซ้ำได้โดยไม่เกิดข้อมูลซ้ำ ตรวจพบปัญหา ติดตามที่มาของผลลัพธ์ และนำข้อมูลไปใช้ต่อได้

แผนนี้อ้างอิงการเทียบเนื้อหาวิชาใน [course_alignment_review.md](course_alignment_review.md) ไม่ใช่เกณฑ์ให้คะแนนที่อาจารย์ยืนยันแล้ว หากได้รับโจทย์หรือ rubric เพิ่มภายหลัง ต้องตรวจเทียบก่อนเพิ่มขอบเขต

## 2. ขอบเขตที่ใช้เป็นหลัก

- คงหัวข้อ RoV vs MLBB และสามแหล่งข้อมูลเดิม
- กำหนดผู้ใช้ตัวอย่างเป็นครีเอเตอร์หรือทีมวิเคราะห์คอนเทนต์เกม ยังเป็นสมมติฐานของโครงงาน ไม่อ้างว่ามีการสัมภาษณ์ผู้ใช้แล้ว
- ทำ historical batch ที่กำหนดช่วงเวลาได้ พร้อมเส้นทางอัปเดตข้อมูลใหม่และหลักฐานตั้งเวลารัน
- ใช้ Python/Pandas และ SQLite โดยย้ายการอ่าน–เขียนจาก Firestore มาเป็นฐานข้อมูลบนเครื่อง พัฒนา orchestration ตามแนวทาง Prefect ที่อยู่ในบทเรียน โดยตรวจ compatibility กับ environment จริงก่อนเลือกเวอร์ชัน
- เก็บ notebook ไว้สำหรับอธิบายและนำเสนอ แยกโค้ด pipeline ที่ใช้ซ้ำออกจากลำดับ cell
- ผลลัพธ์หลักเป็นชุดข้อมูลสรุปและรายงานใน notebook ที่เลือกเกม/ช่วงเวลาได้ ไม่เพิ่มเว็บแอปเป็นเงื่อนไขส่งงานในแผนหลัก
- การทำนายและ sentiment analysis เป็นงานเสริมหลังงานหลักผ่านเกณฑ์ ไม่ใช้เป็นข้อกำหนดเริ่มต้น

คำถามที่ผลลัพธ์ควรช่วยตอบ:

1. ความสนใจค้นหาของสองเกมเปลี่ยนไปอย่างไรในช่วงศึกษาที่ข้อมูลรองรับ?
2. จำนวนคอนเทนต์และการรับชมในกลุ่มช่องที่ศึกษามีรูปแบบอย่างไร?
3. ปริมาณและคะแนนรีวิวเปลี่ยนไปในทิศทางใด และสัมพันธ์กับสัญญาณจากแหล่งอื่นอย่างไรในเชิงพรรณนา?

ไม่ใช้ข้อมูลเหล่านี้ยืนยันจำนวนผู้เล่นทั้งหมด การย้ายเกม หรือเหตุและผลของเหตุการณ์โดยตรง

## 3. เงื่อนไขที่ต้องตรวจในช่วงแรก

ปัจจุบันพบ notebook โปรเจกต์และเอกสารเรียน แต่ยังไม่พบไฟล์ข้อมูลดิบของโปรเจกต์ใน workspace การมี output ใน notebook ไม่เท่ากับมีข้อมูลดิบครบสำหรับรันใหม่

- ตรวจว่ามีไฟล์ข้อมูลเก่าหรือ export จากเพื่อนที่เข้าถึงได้อยู่แล้วหรือไม่ และเก็บ metadata ของข้อมูลนั้น ไม่ขอรหัสผ่านหรือบัญชี Firestore ของเพื่อน
- ตรวจความพร้อมของ API credentials ที่จำเป็น โดยไม่บันทึกค่า secret ใน repository หรือเอกสาร SQLite ไม่ต้องใช้บัญชี cloud
- ตรวจว่าแต่ละแหล่งเก็บข้อมูลย้อนหลังได้ครอบคลุมช่วงที่ต้องการจริงหรือไม่ โดยเฉพาะ Play Store ที่โค้ดเดิมกรองย้อนหลังหนึ่งปีจากวันรัน
- ยังไม่กำหนดช่วงศึกษาจริงโดยเดาจากวันที่ปัจจุบัน ต้องจัดทำ coverage matrix ก่อน แล้วตรึงช่วงเวลาที่อธิบายได้ลง config
- จุดแบ่งสิงหาคม 2025 ต้องมีเหตุผลเชิงโจทย์ ถ้าไม่มีหลักฐานเหตุการณ์ ให้ใช้เป็นการแบ่งช่วงเชิงพรรณนาหรือใช้แนวโน้มรายเดือนเป็นหลัก
- ยังไม่ทราบวันส่งและ rubric จึงจัดแผนตาม dependency และเกณฑ์เสร็จ ไม่ผูกกับวันที่ส่งที่สมมติขึ้น

งานที่ทำได้ระหว่างรอการเข้าถึงข้อมูลจริง: โครงสร้างโค้ด schema ตัวตรวจคุณภาพ การแปลงข้อมูล และการทดสอบด้วย fixture ที่ติดป้ายข้อมูลจำลองชัดเจน ผลจาก fixture ไม่ถือเป็นผลวิจัยจริง

## 4. สถาปัตยกรรมเป้าหมาย

```text
Config: ช่วงศึกษา แหล่งข้อมูล ช่อง/ภาษา และกฎคุณภาพ
                         |
          +--------------+--------------+
          |              |              |
      Trends          YouTube       Play Store
          |              |              |
          +------ Raw + run metadata ---+
                         |
                 Validate and clean
                    /          \
         Rejected + reasons    Clean datasets
                                   |
                    Aggregate each source by game/month
                                   |
                      Join with coverage indicators
                                   |
                    Store and publish completed run
                                   |
                 CSV/Parquet + analysis notebook

Orchestration: dependencies, retries, schedule, run status
Observability: counts, quality results, timestamps, errors
```

Raw เก็บแยกตามแหล่งและรอบ ไม่เขียนทับผลเก่า เฉพาะรอบที่ผ่านเงื่อนไขจึงนำไปเป็นข้อมูลพร้อมใช้ล่าสุด เมื่อรอบหนึ่งผิดพลาด ต้องไม่ทำให้รายงานแสดงข้อมูลบางส่วนเสมือนครบถ้วน

## 5. แผนดำเนินการและเกณฑ์ผ่าน

### ระยะ 1: ตรวจข้อมูลและกำหนดโจทย์

งาน:

- สำรอง notebook ต้นฉบับและบันทึกสถานะก่อนแก้ไข
- ตรวจ data inventory: มีข้อมูลอะไร อยู่ที่ไหน เก็บเมื่อไร จำนวนเท่าไร และขาดอะไร
- ทดลองอ่านข้อมูลจริงขนาดเล็กจากแหล่งที่เข้าถึงได้ ตรวจ schema และช่วงเวลา
- กำหนดช่วงศึกษา ประชากร/กลุ่มตัวอย่าง และรายการช่อง YouTube พร้อมเหตุผลเลือก
- กำหนดว่าจะแสดงผลรายเดือนอย่างไร และใช้ before/after เป็นส่วนใดของคำถาม
- ระบุข้อจำกัด เช่น กลุ่มช่องที่เลือก ข้อมูลรีวิวที่ดึงได้ และข้อจำกัดการระบุผู้ใช้ประเทศไทย

ส่งมอบ: `docs/project_scope.md`, `docs/data_inventory.md`, coverage matrix และ config ของช่วงศึกษา

เกณฑ์ผ่าน: ระบุแหล่งข้อมูล ขอบเขต ผู้ใช้ คำถาม และข้อจำกัดได้ชัด มีหลักฐานข้อมูลจริงตัวอย่าง หรือระบุแหล่งที่ยังเข้าถึงไม่ได้โดยไม่อ้างว่าพร้อมแล้ว

### ระยะ 2: แก้โค้ดเดิมและจัดโครงสร้างให้รันได้

งาน:

- แก้ชื่อไฟล์ `RovPlay.csv`/`rovplay.csv` และลำดับอ่านก่อนสร้างไฟล์
- แก้การลบคอลัมน์ที่อาจไม่มี และการพึ่งตัวแปรค้างใน notebook
- ย้ายค่า path, date, channel และ language ไปอยู่ใน config
- แยก extract/clean/load เป็นฟังก์ชันหรือโมดูล โดยใช้โค้ดเดิมเท่าที่เหมาะสม
- แยกวิธีรัน local pipeline ออกจาก interactive upload/download ของ Colab
- เตรียม dependency list ที่ pin ตาม environment ที่ทดสอบจริง และคู่มือเริ่มต้น
- เพิ่มคำสั่งรันโหมดข้อมูลตัวอย่างและโหมดข้อมูลจริง โดยแยก output ชัดเจน

ส่งมอบ: โครงสร้าง `src/`, config ตัวอย่าง, dependency file และคำสั่งรันหนึ่งจุด

เกณฑ์ผ่าน: จาก environment ที่เตรียมใหม่ สามารถรันกระบวนการกับ fixture ได้ครบ โดยไม่ต้องแก้ตัวแปรหรือจัดไฟล์ระหว่างทาง และผ่าน pilot กับข้อมูลจริงเมื่อ credentials พร้อม

### ระยะ 3: ออกแบบการเก็บข้อมูลและการนำเข้าซ้ำ

งาน:

- ออกแบบ raw/clean/summary และ metadata ของแต่ละรอบ
- ระบุ grain และ key ของทุกชุดข้อมูลใน data dictionary
- เก็บ raw ก่อนตัดคอลัมน์หรือกรอง โดยแยก video/comment หากเก็บ comment มาแล้ว
- ตัดสินใจให้ชัดว่า comments เป็นข้อมูลที่ใช้จริงหรือไม่ ถ้าไม่ใช้ในขอบเขตหลักให้หยุดดึงใหม่เพื่อลดงาน แต่รักษาข้อมูลดิบที่มีอยู่
- เปลี่ยน Firestore loader เป็น SQLite loader พร้อม primary/unique keys และ upsert สำหรับข้อมูลปัจจุบัน
- แยกประวัติยอดวิวเป็น snapshot ตามเวลาเก็บ ไม่ใช้ key ปัจจุบันไปเขียนทับประวัติ
- บันทึก ingestion status, source, query parameters, collected_at และ run_id
- แยกไฟล์ฐานข้อมูลและ output สำหรับ sample/test ออกจากข้อมูลจริง รองรับ import CSV/JSON โดยรักษาไฟล์ต้นฉบับ

ตัวอย่าง grain ที่ต้องระบุ:

| Dataset | หนึ่งแถวแทนอะไร | แนวทาง key |
|---|---|---|
| Video metadata | วิดีโอหนึ่งรายการ | `video_id` |
| Video statistics snapshot | สถิติวิดีโอหนึ่งรายการ ณ รอบเก็บหนึ่งครั้ง | `video_id + snapshot_id` |
| Review current | รีวิวหนึ่งรายการของหนึ่งแอป | `app_id + review_id` |
| Trend observation | ค่าค้นหาของคำ/หัวข้อในบริบทคำขอและเวลาหนึ่ง | รวม query context, window และ observation timestamp |
| Monthly summary | เกมหนึ่งเกมในเดือนหนึ่ง ภายใต้ dataset version เดียว | `dataset_version + game + month` |

เกณฑ์ผ่าน: นำ batch เดิมเข้าซ้ำแล้วจำนวน logical records ไม่เพิ่ม; update ข้อมูลเดิมได้ตามนโยบาย; snapshot ใหม่เก็บประวัติได้; ระบุ raw ที่ใช้สร้างผลลัพธ์แต่ละรอบได้

### ระยะ 4: ทำความสะอาดและตรวจคุณภาพ

งาน:

- กำหนดชนิดข้อมูล timezone และชื่อเกมให้สอดคล้องกัน
- ตรวจ required fields, duplicate keys, dates, rating 1–5 และจำนวนที่ไม่ติดลบ
- แยกข้อมูลที่ไม่ผ่านกฎพร้อมเหตุผล ไม่ตัดทิ้งโดยไม่มีบันทึก
- จัดการ missing values ตามความหมาย ห้ามเปลี่ยนข้อมูลที่ดึงไม่สำเร็จเป็นศูนย์
- ตรวจการจำแนกเกมจากชื่อวิดีโอด้วยตัวอย่างที่มนุษย์ตรวจ รวมทั้งกรณีทั้งสองเกม/ไม่เข้ากฎ
- ตรวจความครบของ pagination และการตอบกลับว่าง แยก no data ออกจาก request failed
- ตรวจ baseline ของ Trends ด้วยวันจริงแทนตำแหน่งแถว และตรวจการเทียบสเกลข้าม request/window ตามเอกสารต้นทางก่อนสรุปแนวโน้ม
- กำหนด hard failures ที่ต้องหยุด เช่น schema สำคัญหายหรือ key ไม่เป็นเอกลักษณ์ และ warnings ที่รายงานพร้อมผลได้

ส่งมอบ: กฎคุณภาพ, clean/rejected datasets และรายงานจำนวนก่อน–หลังแปลงรายแหล่ง

เกณฑ์ผ่าน: จำนวน input อธิบายย้อนกลับไปยัง kept/rejected/deduplicated ได้; valid dataset ผ่านกฎที่กำหนด; fixture ที่จงใจผิดถูกตรวจพบ; report ระบุ missing coverage ได้

### ระยะ 5: เชื่อมข้อมูลและสร้างตัวชี้วัด

งาน:

- สรุปแต่ละแหล่งให้เหลือหนึ่งเกมต่อเดือนก่อน join
- ใช้ปฏิทินเดือนที่กำหนดเป็นฐานเพื่อให้เห็นเดือนที่ขาด ไม่ใช้ inner join แล้วทำให้ช่วงที่ขาดหายไปเงียบ ๆ
- ตรวจ uniqueness ก่อน join และตรวจจำนวนแถวหลัง join เพื่อป้องกัน many-to-many
- กำหนดสูตรตัวชี้วัดพร้อมขอบเขตและตัวหารที่ชัดเจน
- เก็บ review count คู่กับ mean rating เพื่อเห็นขนาดตัวอย่าง
- เก็บ video count และ median views ณ วันเก็บ โดยระบุว่าไม่ใช่ยอดวิวที่เกิดภายในเดือนเผยแพร่
- หากทำ growth ให้ใช้เฉพาะช่วงที่มี coverage และสเกลเทียบกันได้ จัดการฐานศูนย์/ค่าว่างโดยไม่สร้างค่าที่ชวนเข้าใจผิด
- รักษาข้อมูลแต่ละแหล่งไว้แยกกันด้วย เพื่อให้ตรวจย้อนกลับได้

ส่งมอบ: `monthly_game_metrics`, export CSV/Parquet, data dictionary และคำอธิบายสูตร

เกณฑ์ผ่าน: key เดือน–เกมไม่ซ้ำ; ไม่มีแถวคูณจาก join; ค่าตัวอย่างตรวจคำนวณด้วยมือได้; ไม่เติมศูนย์ให้ข้อมูลที่ไม่ทราบ; ตัวชี้วัดที่เปรียบเทียบกันระบุบริบทเวลาได้

### ระยะ 6: จัดลำดับ ตั้งเวลา และรับมือความล้มเหลว

งาน:

- ต่อ tasks ตาม dependency ของ extract → raw → clean → summarize → publish
- แยก historical backfill ออกจาก update โดยเลือกกลยุทธ์ตามความสามารถของแต่ละแหล่ง ไม่สมมติว่าทุก API รองรับ incremental cursor
- เพิ่ม retry เฉพาะปัญหาชั่วคราว พร้อม timeout/backoff และเคารพข้อจำกัดของผู้ให้บริการ
- เก็บ run status, duration, row counts และ error ที่ใช้วิเคราะห์ปัญหาได้
- ป้องกันการทำงานซ้อนของ batch เดียว และรองรับเริ่มใหม่หลังบาง task ล้มเหลว
- กำหนดเงื่อนไข publish เมื่อข้อมูลพร้อม ส่วนแหล่งที่ไม่ครบต้องแสดงสถานะ หรือคงชุดสำเร็จล่าสุดตามนโยบาย
- ทดลอง schedule กับรอบเล็กที่ไม่สร้างภาระ API เกินจำเป็น และบันทึกประวัติการรันตามเวลาจริง

ส่งมอบ: flow, deployment/schedule configuration, run logs และภาพหลักฐานสถานะการทำงาน

เกณฑ์ผ่าน: แสดง scheduled run สำเร็จ; จำลอง transient failure แล้ว retry ได้; permanent failure ไม่ถูกประกาศเป็น success; การ rerun ไม่สร้างข้อมูลซ้ำ; ผลที่เผยแพร่ระบุรอบที่สร้างได้

### ระยะ 7: วิเคราะห์และจัดทำรายงานสำหรับผู้ใช้

งาน:

- ทำ notebook นำเสนอที่อ่านจากชุดข้อมูลพร้อมใช้ของรอบที่สำเร็จ
- ให้เลือกเกมและช่วงเวลาได้ผ่าน parameter หรือ controls ใน notebook
- แสดงการค้นหา จำนวนคอนเทนต์ การรับชมตามนิยามที่กำหนด คะแนนและจำนวนรีวิว
- แสดงวันเก็บ/วันอัปเดตล่าสุด ขอบเขตกลุ่มตัวอย่าง และสถานะความครบถ้วน
- เขียนข้อค้นพบจากผลจริง เชื่อมกลับกับคำถามตั้งต้น พร้อมข้อจำกัด
- หากเปรียบเทียบ before/after ต้องคำนึงถึงความยาวช่วง จำนวนช่อง และอายุวิดีโอ ไม่สรุป causal effect จากกราฟก่อน–หลังอย่างเดียว
- แยกรายงานตัวชี้วัดเกมออกจากรายงานสุขภาพ pipeline เพื่อให้ผู้ใช้ดูเข้าใจ

ส่งมอบ: analysis notebook, ภาพกราฟที่ใช้ในรายงาน และบทสรุปผลที่มีหลักฐาน

เกณฑ์ผ่าน: ตัวเลขบนกราฟตรงกับ export ของ run เดียวกัน; ตัวกรองทำงานถูกต้อง; ข้อมูลจำลองไม่ปะปนกับผลจริง; ข้อสรุปไม่เกินสิ่งที่ข้อมูลรองรับ

### ระยะ 8: ตรวจรับและเตรียมส่ง

## 7. โครงรายงานและเรื่องที่จะเล่าให้อาจารย์ฟัง

1. ปัญหา ผู้ใช้ และคำถามที่ต้องการตอบ
2. แหล่งข้อมูล วิธีเลือกกลุ่มตัวอย่าง และข้อจำกัด
3. สถาปัตยกรรม pipeline และเหตุผลเลือกเครื่องมือ
4. Data model, grain, keys และการเก็บประวัติ
5. ตัวอย่างปัญหาข้อมูลจริง กฎทำความสะอาด และผลตรวจคุณภาพ
6. การเชื่อมข้อมูลและตัวชี้วัดที่สร้างขึ้น
7. Orchestration และการรับมือกรณีผิดพลาด
8. ผลวิเคราะห์ที่ตอบคำถามตั้งต้น
9. ผลทดสอบ ความสามารถในการรันซ้ำ และสิ่งที่ยังเป็นข้อจำกัด

ลำดับ demo: แสดงแผนผัง → สั่งรันรอบเล็ก → ดู raw/quality → ดูชุดข้อมูลรวม → ดูรายงาน → rerun batch เดิมและตรวจจำนวน → แสดงหลักฐาน retry/failure handling

## 9. ลำดับความสำคัญเมื่อเวลาจำกัด

รักษางานหลัก: ข้อมูลจริงที่มีที่มา → pipeline ที่ถูกต้อง → raw/clean/summary → key และคุณภาพ → ชุดข้อมูลเชื่อมข้ามแหล่ง → หลักฐานรันซ้ำ/ตั้งเวลา → รายงานและ demo

ลดงานตกแต่งและงานเสริมก่อน ได้แก่ เว็บแอปเต็มรูปแบบ sentiment analysis โมเดลทำนาย การเพิ่มแหล่งข้อมูล และการย้ายไปหลายบริการ cloud สิ่งเหล่านี้ไม่ควรเบียดเวลาตรวจความถูกต้องของงานหลัก

ขั้นตอนส่งมอบ: ตรวจรายการไฟล์และ secret, ตรวจรันจากโฟลเดอร์ที่ย้ายตำแหน่งได้ แล้วอัปโหลด repository ที่ผู้ใช้ระบุ โดยไม่ส่ง raw ของทีม/credentials/เอกสารเรียน

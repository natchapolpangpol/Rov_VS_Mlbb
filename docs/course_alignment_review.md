## ข้อสรุปและขอบเขต

จากเนื้อหาวิชา ควรเพิ่มน้ำหนักของโปรเจกต์ไปที่การสร้างกระบวนการจัดเตรียมข้อมูลที่ครบวงจร เชื่อมข้อมูลหลายแหล่ง ตรวจคุณภาพ รันซ้ำได้ และส่งมอบข้อมูลให้ผู้ใช้ที่ระบุชัดเจน การวิเคราะห์และกราฟเป็นปลายทางหนึ่งของกระบวนการนี้

นี่คือการตีความจากเนื้อหาการสอน ไม่ใช่การยืนยันเจตนาของอาจารย์หรือเกณฑ์ให้คะแนนโปรเจกต์ ในโฟลเดอร์ที่ตรวจไม่พบเอกสารโจทย์โปรเจกต์หรือ rubric แยกต่างหาก เนื้อหาที่สอนจึงไม่เท่ากับข้อบังคับว่าต้องใช้เครื่องมือทุกตัว

ขอบเขตการอ่าน: สไลด์ PDF 10 บท รวม 279 หน้า เนื้อหาและโจทย์ใน notebook 24 ไฟล์ของ Lab 1–10 ตรวจโครงสร้างชุดข้อมูลประกอบ CSV/JSON/SQLite และอ่าน source ของ `RovVsMlbb_Pipeline.ipynb` เทียบกับบทเรียน ตรวจภาพสไลด์ที่เกี่ยวข้องโดยเฉพาะเมื่อข้อความภาษาไทยที่สกัดจาก PDF ผิดรูป ไม่ได้รัน notebook หรือเชื่อมต่อฐานข้อมูลจริง การประเมินโปรเจกต์ด้านล่างจึงเป็นการตรวจโค้ด ไม่ใช่ผลทดสอบการทำงานจริง

ใช้สไลด์และข้อความโจทย์เป็นหลักในการตีความความคาดหวัง ไม่ถือว่าโค้ดคำตอบทุก cell เป็นข้อกำหนดหรือเฉลยที่ตรวจแล้ว นอกจากนี้ README ของ Lab 04 ระบุว่า `lab04_users.csv` เป็นข้อมูลจำลองทดแทนไฟล์ที่ถูกลบ จึงไม่ใช้ผลตัวเลขจากไฟล์นั้นอ้างเป็นผลต้นฉบับของอาจารย์

## จุดที่ควรแก้ก่อนเพิ่มฟีเจอร์

1. **การโหลดซ้ำเข้า Firestore:** cell 42 เรียก `col_ref.document()` โดยไม่กำหนด ID ดังนั้นการส่งข้อมูลเดิมซ้ำจะสร้างเอกสารใหม่ การลบซ้ำใน DataFrame ก่อนโหลดไม่ได้ป้องกันซ้ำระหว่างรอบ ต้องกำหนด business key สำหรับข้อมูลปัจจุบัน และแยก key สำหรับ snapshot/history ตามวัตถุประสงค์
2. **ข้อมูลดิบถูกเขียนทับ:** cell 36 ตัด comment และเขียนกลับไฟล์เดิม ควรเก็บ raw แยกจาก clean เพื่อประมวลผลใหม่ได้ การตัด comment ออกจากตารางวิดีโอช่วยรักษาระดับหนึ่งแถวต่อวิดีโอ แต่ไม่จำเป็นต้องทำให้ข้อมูลดิบหาย
3. **ช่วงเวลาไม่ตรงกัน:** Trends ใช้วันสิ้นสุดคงที่ 2026-02-01; YouTube ถึง 2026-03-10; Play Store ใช้ย้อนหลังหนึ่งปีจากเวลาที่รัน ควรกำหนดช่วงศึกษาและวันอ้างอิงให้ชัด พร้อมรายงาน coverage ของแต่ละแหล่ง
4. **เส้นทางไฟล์ยังไม่ต่อเนื่อง:** cell 33–34 เขียน `RovPlay.csv`/`MlbbPlay.csv` แต่ cell 54/56 อ่านชื่อพิมพ์เล็กใน `/content/`; cell 32 อ่านไฟล์ MLBB ก่อนขั้นตอน export ใน notebook และผลกรองของ cell นี้ไม่ได้เป็นตัวที่ export ใน cell 34 ต้องตรวจให้รันจากสภาพเริ่มต้นได้
5. **คอลัมน์ที่คาดหวังไม่ตรงกัน:** cell 54/56 ลบ `index` แบบไม่ตรวจว่ามีอยู่ ขณะที่ขั้นตอน export ใช้ `index=False` จึงมีเส้นทางที่เกิดข้อผิดพลาดได้
6. **คุณภาพก่อนนำเสนอ:** cell 66 ตัดแถว `score` ว่างก่อนแปลงเป็นตัวเลข แต่ไม่ได้ตรวจซ้ำหลัง `errors='coerce'` หรือบังคับช่วง 1–5 ควรรายงานและแยกข้อมูลที่แปลงไม่ได้
7. **ความหมายเวลา YouTube:** `views` คือสถิติที่ดึงมาในรอบเก็บ ไม่ได้เป็นยอดวิวที่เกิดภายในเดือนเผยแพร่วิดีโอ และไม่มี `collected_at` ในแถวปัจจุบัน ต้องระบุความหมายให้ชัดเมื่อเปรียบเทียบก่อน/หลังหรือรวมรายเดือน
8. **กฎจำแนกเกม:** cell 19 ใช้การค้นคำแบบ case-sensitive และทิ้งชื่อที่พบทั้งสองเกมหรือไม่พบคำที่กำหนด ควรรายงานจำนวนที่ไม่เข้ากฎและตรวจตัวอย่าง เพื่อให้ผู้ใช้เข้าใจขอบเขตของชุดข้อมูล
9. **วันที่และการปรับสเกล Trends:** cell 10/12 ผูก baseline ด้วยตำแหน่ง `iloc[i]` ทั้งที่ช่วงเริ่มต้นต่างกัน ควรตรวจการจับคู่ด้วยวันจริงก่อนเชื่อผล ส่วน cell 14 ต่อผลคำขอหลายช่วงเข้าด้วยกัน ควรตรวจวิธีทำให้สเกลข้ามช่วงเทียบกันได้ก่อนใช้สรุปแนวโน้มระยะยาว

ข้อ 7–9 เป็นประเด็นที่ต้องตรวจและอธิบายเพิ่มเติม ไม่ใช่ผลยืนยันว่าข้อมูลจริงผิดทั้งหมด การตรวจครั้งนี้ยังไม่ได้ประเมินข้อมูลที่อยู่ใน Firestore

**แนวคิด:** ระบบจัดเตรียมและติดตามข้อมูลความสนใจต่อ RoV และ MLBB สำหรับผู้วิเคราะห์คอนเทนต์เกม

ผู้ใช้ตัวอย่างคือครีเอเตอร์หรือทีมวิเคราะห์คอนเทนต์ ซึ่งต้องการดูการเปลี่ยนแปลงของการค้นหา การผลิต/รับชมคอนเทนต์ และการให้คะแนนรีวิว เพื่อประกอบการวางแผน ไม่อ้างว่าข้อมูลนี้ยืนยันจำนวนผู้เล่นหรือการย้ายเกมได้โดยตรง

### 1. ทำให้กระบวนการเดิมรันซ้ำได้

- กำหนดช่วงเวลา ช่องที่เก็บ และภาษาไว้ใน config
- เก็บ raw ตามแหล่งข้อมูลและรอบเก็บ พร้อม `run_id`/`collected_at`
- แยก clean ออกจาก raw และเก็บรายการที่ไม่ผ่านเกณฑ์พร้อมเหตุผล
- กำหนด key ป้องกันการนำเข้าข้อมูลเดิมซ้ำ และออกแบบ history เฉพาะข้อมูลที่จำเป็น
- แก้ชื่อไฟล์ ตัวแปรและคอลัมน์ให้กระบวนการต่อกันจากต้นถึงปลาย

### 2. สร้างชุดข้อมูลเชื่อมข้ามแหล่ง

เสนอให้เริ่มด้วย grain **หนึ่งเกมต่อหนึ่งเดือน** และสรุปแต่ละแหล่งให้ได้ grain นี้ก่อน join ห้ามเอารีวิวรายรายการไป join กับวิดีโอรายรายการด้วยชื่อเกมอย่างเดียว เพราะจำนวนแถวอาจคูณกัน

ตัวอย่าง schema ที่เสนอ ไม่ใช่ข้อมูลผลลัพธ์จริง:

| ฟิลด์ | ความหมาย |
|---|---|
| `month`, `game` | คีย์ของชุดข้อมูลสรุป |
| `search_interest` | ดัชนีความสนใจที่ผ่านการตรวจวิธีเทียบสเกลแล้ว |
| `published_video_count` | จำนวนวิดีโอที่เผยแพร่ในเดือนนั้นในกลุ่มช่องที่ศึกษา |
| `median_views_at_collection` | มัธยฐานยอดวิวสะสม ณ วันเก็บ ของวิดีโอที่เผยแพร่เดือนนั้น |
| `review_count` | จำนวนรีวิวในชุดข้อมูลหลังผ่านกฎที่ระบุ |
| `mean_review_rating` | ค่าเฉลี่ยคะแนนรีวิวในเดือนนั้น |
| `source_coverage` | สถานะความครบถ้วนของข้อมูลแต่ละแหล่ง |
| `run_id`, `collected_at` | รอบและเวลาที่ใช้สร้างผลลัพธ์ |

การทำ grain ให้ตรงกันช่วยเชื่อมข้อมูลได้ แต่ไม่ได้ทำให้ตัวชี้วัดต่างความหมายกลายเป็นสิ่งเดียวกัน ต้องอธิบายเวลาที่เกิดเหตุการณ์และเวลาที่เก็บสถิติด้วย หากเริ่มเก็บ snapshot ยอดวิวต่อเนื่องในอนาคต จึงค่อยออกแบบตัวชี้วัดการเปลี่ยนแปลงระหว่างรอบตาม coverage ที่มี

ไม่ต้องฝืนรวมทุกแหล่งเป็นคะแนนความนิยมเดียว หากยังไม่มีเหตุผลรองรับสูตรและน้ำหนัก

### 3. จัดลำดับและติดตามการทำงาน

เลือกรูปแบบ batch ที่เหมาะกับความถี่ที่ต้องใช้ข้อมูล โดยแยกการเก็บข้อมูลย้อนหลังครั้งแรกออกจากรอบอัปเดต

ลำดับงานที่เสนอ: extract → save raw → validate/clean → aggregate/integrate → load → publish output

เลือกเครื่องมือหนึ่งตัวจากแนวทางที่เรียน และทำให้เห็นการตั้งเวลา dependency การลองใหม่เมื่อเกิดปัญหาชั่วคราว และประวัติการทำงาน ถ้าเลือกงานย้อนหลังช่วงเวลาตายตัว อาจเน้นการรันซ้ำด้วย parameter และตรวจสอบย้อนกลับ โดยไม่จำเป็นต้องดึงข้อมูลเดิมทุกวัน

### 4. ส่งมอบผลลัพธ์พร้อมหลักฐานคุณภาพ

- ชุดข้อมูลสำหรับวิเคราะห์ร่วม พร้อม data dictionary และสูตรตัวชี้วัด
- รายงานหรือ dashboard ที่เลือกเกมและช่วงเวลาได้ พร้อมวันอัปเดตล่าสุด
- รายงานคุณภาพ: แถวรับเข้า แถวซ้ำ แถวไม่ผ่าน ช่วงเวลาขาด และแถวที่ join ไม่สำเร็จ
- หลักฐานสาธิตว่ารัน input เดิมซ้ำแล้วจำนวนข้อมูลไม่เพิ่มเพราะข้อมูลซ้ำ และเมื่อแหล่งหนึ่งล้มเหลว ระบบแสดงสถานะได้ถูกต้อง

การเพิ่มโมเดลทำนายหรือ sentiment analysis เป็นทางเลือกเมื่อมีโจทย์ปลายทางรองรับ ไม่ใช่สิ่งที่อนุมานว่าอาจารย์บังคับจากเอกสารชุดนี้ เช่นเดียวกับการใช้ Hadoop, Airflow หรือทุกบริการ GCP ซึ่งควรเลือกตามขนาดและความต้องการของงาน
